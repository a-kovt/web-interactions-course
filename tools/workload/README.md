# Допоміжний засіб HTTP-навантаження

Засіб виконує вашу функцію `scenario(ctx)` багато разів і записує результати
HTTP-звернень. Потрібен Python 3.14. Сторонніх залежностей немає.
Сервіс, клієнт проєкту, предметні перевірки та сценарії демонстрації пише команда.
Використання цього засобу необов'язкове й не додає критеріїв до лабораторних робіт.

## Файли та розміщення

| Файл | Призначення |
|---|---|
| `run.py` | Запуск сценаріїв із заданою інтенсивністю та обмеженням паралелізму |
| `client.py` | HTTP-запит, перевірка статусу, опитування стану, обмеження часу |
| `results.py` | CSV вимірів і підсумок JSON |

Засіб розміщено в `tools/workload/` поруч із прикладами сценаріїв `scenario.example.py` і `load.example.py`.
Команди нижче виконуйте з кореня проєкту. У спільному проєкті засіб є в обох частинах і
однаковий. Тоді виконуйте команди з кореня спільного проєкту й вказуйте шлях `web/tools/workload/run.py`.

```text
project/
  tools/workload/
  joint/
```

## Сценарій і контракт

Сценарій – ваш Python-файл із функцією `scenario(ctx)`. Він є виконуваним кодом,
тому використовуйте лише власні або перевірені файли. Необов'язкова функція
`validate(bases, settings)` перевіряє налаштування до початку навантаження.

OpenAPI описує запити й відповіді вашого API. Засіб не читає його автоматично.
За цим описом команда задає маршрути, поля, очікувані статуси та послідовність дій.
Умовний сценарій нижче використовує `api` і `resource_id`. Параметри прикладу комплекту наведено нижче.

| Операція | Поведінка |
|---|---|
| `ctx.request(method, path, ...)` | Один HTTP-запит, типово очікується 200. `expected=(201,)` задає інші припустимі статуси |
| `response.json()` | Розбір тіла JSON. `response.headers` містить назви заголовків малими літерами |
| `ctx.check(condition)` | Позначає сценарій невдалим, якщо умова хибна |
| `ctx.poll(path, done, ...)` | Повторює GET, доки ваша функція `done(response)` не поверне істину або не спливе час |
| `ctx.wait(seconds)` | Пауза з урахуванням припинення роботи й часу сценарію |
| `ctx.settings` | Значення з `--set` і `--env` |
| `ctx.random` | Окремий генератор випадкових чисел для кожного запуску сценарію |
| `ctx.index` | Номер запуску сценарію, починаючи з 0 |

Засіб не повторює невдалі запити автоматично й не переходить за перенаправленнями.
Якщо дослід потребує повтору, явно задайте його в сценарії, збережіть той самий
ключ операції та врахуйте `Retry-After` за контрактом. Токени й `If-Match` також
передаються сценарієм. Підтримка HTTP у засобі не реалізує механізм ідемпотентності,
контроль версій або відновлення клієнта у вашому застосунку.

## Приклад комплекту

`scenario.example.py` – одна пара конкурентних бронювань через `app-a` і `app-b` (О2.1).
Команда запуску наведена в шапці файлу, параметри –
`--base a=... --base b=... --set tokens_file=tokens.txt --set book_id=b-one --runs 2 --rate 100 --concurrency 2`.

Файл токенів містить токени **двох різних читачів**. Різні токени одного читача не підходять.
Бар’єр узгоджує початок двох запитів, але не гарантує їх перекриття всередині сервера.
Перед дослідом доступний один примірник і немає активних бронювань цих читачів.
Після нього очікуються один статус 201, один 409 та одне активне бронювання в базі.
Сценарій призначений для однієї пари. Для тривалого навантаження потрібен інший сценарій.

`load.example.py` – тривале навантаження для О6.4: бронювання з новим ключем
ідемпотентності, читання й скасування. Відповіді `429` і `503` сценарій повторює з тим самим
ключем після `Retry-After`, `409` вважає відмовою за предметними правилами. Команда запуску –
у шапці файлу. Запустіть її, поки в іншому терміналі `tools/rolling-update.sh` замінює
екземпляри. `requests.csv` і `summary.json` містять статус і мітку кожної спроби, а правило
підрахунку помилок для О6.4 визначає команда.
Файл токенів містить токени кількох читачів. Якщо читач уже бронює цю книгу, буде `409`.

## Запуск власного сценарію

Спочатку підготуйте власний сервіс, міграції, потрібні ресурси й облікові записи.
Команди нижче стосуються власного `tools/workload/my-scenario.py`, який приймає `api`, `token` і `resource_id`. Це не команди запуску прикладу комплекту.
Команди наведено для Bash. Змінну `API_TOKEN` треба заздалегідь встановити в середовищі.

Один запуск із паузою після кожної відповіді.

```sh
uv run --no-project --python 3.14 python tools/workload/run.py tools/workload/my-scenario.py \
  --base api=http://localhost:8080 --env token=API_TOKEN \
  --set resource_id=resource-1 --runs 1 --pause 1 --out runs/demo-01
```

Навантаження протягом хвилини.

```sh
uv run --no-project --python 3.14 python tools/workload/run.py tools/workload/my-scenario.py \
  --base api=http://localhost:8080 --env token=API_TOKEN \
  --set resource_id=resource-1 --duration 60 --rate 20 --concurrency 10 \
  --scenario-timeout 30 --out runs/load-01
```

`--rate` – бажана кількість **початків сценаріїв**, а не HTTP-запитів за секунду.
Один сценарій може зробити кілька запитів. `--concurrency` обмежує кількість
одночасних сценаріїв. Якщо всі виконавці зайняті, черговий запуск пропускається.
Засіб не створює необмежену чергу й не надолужує пропущені запуски сплеском.
Планування на клієнті не гарантує точної частоти надходження запитів до сервера.

`--duration` обмежує час початку нових сценаріїв. Після нього засіб чекає завершення
вже запущених. Альтернатива – `--runs N`, кількість фактично запущених сценаріїв.
Типово виконується один сценарій. `--timeout` – тайм-аут сокета HTTP (5 с),
`--scenario-timeout` – час сценарію (30 с), який перевіряється між операціями.
Власні нескінченні цикли чи блокувальні виклики сценарію засіб примусово не зупиняє.
Читання відповіді також залежить від поведінки мережі. Це не жорсткий загальний
тайм-аут HTTP. Обсяг однієї відповіді обмежено 1 МіБ.

Ctrl+C припиняє нові запуски. Активні сценарії завершуються через перевірки
контексту й мережеві тайм-аути. Часткові результати зберігаються.
`--seed` відтворює вибір із `ctx.random`, але не порядок конкурентного виконання,
мережеві затримки чи UUID. Каталог `--out` має бути новим, бо наявні результати
не перезаписуються. Засіб не відкочує виконані операції й не очищає базу.

## Результати

`requests.csv` містить номер сценарію, мітку кроку, метод, ім'я сервісу, HTTP-статус,
тривалість спроби та її результат. Статус 0 означає, що повної відповіді
не отримано: немає з'єднання, сплив тайм-аут, тіло обірване або перевищує 1 МіБ. Тіла, адреси запитів і токени не записуються. Не вставляйте секрети
у власні мітки кроків. Вивід помилок містить лише клас винятку.

`summary.json` містить лічильники запитів і сценаріїв, пропущені запуски та
перцентилі затримки останніх 10 000 HTTP-спроб. У CSV є всі спроби. Для перцентилів
усього довгого досліду обробіть CSV окремо. Це затримки клієнта, а не час усередині сервісу.
Пауза після відповіді не входить до затримки запиту.

Коди завершення засобу:

- 0 – сценарії не завершилися винятками
- 1 – є невдалі або зупинені сценарії
- 2 – помилка налаштувань
- 130 – переривання Ctrl+C

Статус, явно включений у `expected`, не є помилкою. Наприклад, усі запити можуть
отримати очікуваний 429. Сценарії завершаться без винятків, але корисної роботи
сервіс не виконає. Аналізуйте лічильники статусів, а не лише код завершення.
Успішний запуск не засвідчує виконання всіх критеріїв лабораторної роботи.

### Поля файлів результатів

| Поле CSV | Значення |
|---|---|
| `scenario` | Номер запуску від 0 |
| `label`, `method`, `service` | Мітка кроку, HTTP-метод, ім’я з `--base` |
| `status` | HTTP-статус; 0 – повної відповіді не отримано |
| `seconds` | Тривалість HTTP-спроби в секундах, включно з читанням тіла |
| `outcome` | `expected` – статус дозволений; `unexpected_status` – інший статус; `transport_error` – повної відповіді немає |

| Поле JSON | Значення |
|---|---|
| `elapsed_seconds` | Загальна тривалість виконання сценаріїв у секундах, включно з очікуванням активних сценаріїв |
| `requests` | Кількість записаних HTTP-спроб |
| `http_statuses`, `request_outcomes` | Лічильники статусів і результатів HTTP-спроб |
| `scenarios` | Кількість `passed`, `failed`, `stopped`. Відсутня категорія означає нуль |
| `skipped_starts` | Пропущені початки через зайнятість усіх виконавців |
| `interrupted` | Ознака переривання користувачем |
| `request_latency_seconds` | `p50`, `p95`, `p99` у секундах або `null`, якщо спроб не було |
| `latency_sample_count` | Кількість спроб у вибірці перцентилів, не більше 10 000 |
| `latency_sample_policy` | Останні завершені HTTP-спроби, включно з невдалими |

Умовний приклад. `requests=20` і `http_statuses={"201":1,"409":19}` означають одну
успішну відповідь створення й 19 відмов. Це ще не доводить збереження інваріанта,
бо потрібна перевірка кінцевого стану. Приклад не є результатом вимірювання комплекту.
