# Налаштування перевірки (`checks.yaml`)

Засіб перевірки викладача звертається до запущеного стенда як зовнішній клієнт. Він читає два
файли проєкту. З `openapi.yaml` він бере маршрути, ролі операцій і приклади тіл, а з
`checks.yaml` – те, чого контракт не каже. Скопіюйте [checks.example.yaml](../checks.example.yaml)
як `checks.yaml` у корінь проєкту поруч з `openapi.yaml`.

## Пункти (`items`)

Номери пунктів беруться з методички ЛР. Пункти з позначкою «Ядро» перевіряються завжди, їх у
`items` не пишуть. У `items` перелічують лише виконані пункти поза ядром. Невдала перевірка
невибраного пункту дає SKIP, а не FAIL. Невідомий номер зупиняє запуск. Літери можна писати
кирилицею (`О1.5`, `Д2.1`) або латиницею (`O1.5`, `D2.1`).

```yaml
items: [О1.5, О1.6, О2.3, Д2.1]
```

## Що засіб бере з контракту

Службові маршрути (`/health`, `/ready`, `/metrics`, `/v1/auth/...`, `/v1/me`, `/v1/ws`) однакові для
всіх тем. Залиште їх такими, як у [openapi.example.yaml](../openapi.example.yaml).

Роль предметної операції позначають полем `x-course` в описі операції:

| `x-course` | Операція | Без позначки знаходиться як |
|---|---|---|
| `main` | головна операція | `POST`, `PUT` або `PATCH` з обов'язковим `Idempotency-Key` і відповіддю 200, 201 чи 204 |
| `list` | список | `GET` із параметром `cursor` |
| `object` | один об'єкт | `GET` ресурсу головної операції з `/{id}` |
| `long-operation` | довга операція | `POST` із відповіддю 202 |
| `cancel`, `update`, `staff-action` | скасування, зміна, дія персоналу | лише позначкою |

Тіла запитів засіб бере з іменованих прикладів (`examples`) операції. Значення в них мають
існувати в демоданих проєкту:

- головна операція – `normal` (звичайний успішний запит), `scarce` з `x-capacity: N` (ресурс із N
  одиницями для гонки й 409), `missing` (ресурсу немає, 404)
- зміна об'єкта (`update`) – `normal` і `forbidden` (зміна полів власника, стану чи версії, 422)

Рядок `{uuid}` у прикладі в кожному запиті стає новим ідентифікатором. Для перевірки потрібні два
звичайні користувачі й один співробітник у демоданих. Їхні логіни й паролі викладач передає засобу
під час запуску.

## Приклад

У прикладі «Міська бібліотека» головна операція – бронювання примірника `POST /v1/holds`.
Вона реалізує пункти О1.4 (головна операція), О2.1 (інваріант за одночасних запитів) й О2.2
(механізм ідемпотентності). Запит має заголовок `Idempotency-Key` і тіло з `book_id` та `branch_id`.
Сервер в одній транзакції PostgreSQL перевіряє залишок примірників у філії, зменшує його й
створює бронювання.

Засобу треба знати, яка операція головна і які тіла надсилати. Тому в `openapi.yaml` операцію
позначено `x-course: main`, а її приклади посилаються на книги з демоданих.

```yaml
/v1/holds:
  post:
    x-course: main
    parameters:
      - $ref: "#/components/parameters/IdempotencyKey"
    requestBody:
      content:
        application/json:
          examples:
            normal:
              value: {book_id: b01, branch_id: central}
            scarce:
              value: {book_id: b-one, branch_id: central}
              x-capacity: 1
            missing:
              value: {book_id: no-such-book, branch_id: central}
```

З цього опису засіб бере все потрібне. Для О1.4 він надсилає `normal` і чекає 201 з `Location`,
а `missing` – і чекає 404. Для О2.1 він надсилає 20 одночасних запитів `scarce` і перевіряє, що
успіхів не більше, ніж `x-capacity`, а решта отримали 409. Для О2.2 він повторює `normal` з тим
самим ключем. Книга `b-one` з одним вільним примірником має бути в міграції з демоданими,
інакше перевірка гонки не має сенсу. У `checks.yaml` для цієї операції нічого писати не треба.

Без позначки `x-course` ту саму операцію описують у `checks.yaml`.

```yaml
roles:
  main: {method: POST, path: /v1/holds}
```

Те, чого в контракті немає, задають лише в `checks.yaml`. Наприклад, ліміт змін Д2.1 сервер бере
зі змінної `RATE_LIMIT_PER_MIN` у `.env`, і засіб має знати те саме число, щоб перевищити його
й отримати 429.

```yaml
items: [Д2.1]
rate_limit: 120
```

## Ключі `checks.yaml`

Усі ключі необов'язкові. Задавайте лише ті, що відрізняються від типових значень.

| Ключ | Що задає | Звідки взяти |
|---|---|---|
| `items` | вибрані пункти поза ядром | методичка ЛР |
| `roles` | роль, метод, шлях і приклади операції, якщо `x-course` не використано | ваш `openapi.yaml` |
| `role_names` | назви двох ролей у відповіді `GET /v1/me` (типово `user`, `staff`) | ваша модель користувачів |
| `login` | маршрут входу, якщо не `/v1/auth/login` | ваш `openapi.yaml` |
| `instances` | прямі адреси `app-a` і `app-b` | опубліковані порти `compose.yaml` |
| `gateways`, `ws` | прямі адреси шлюзів, адреса WebSocket, якщо вона інша | опубліковані порти `compose.yaml` |
| `services` | імена сервісів, якщо їх змінено | `compose.yaml` |
| `log_fields` | імена полів журналу JSON для ключів `time`, `instance`, `route`, `status`, `duration`, якщо засіб їх не впізнає (типово `time`, `instance`, `route`, `status`, `duration_ms`) | ваш формат журналу |
| `rate_limit` | ліміт змін за хвилину (Д2.1) | налаштування `RATE_LIMIT_PER_MIN` |
| `heartbeat_s` | період контрольних сигналів WebSocket (Д5.5) | ваша реалізація шлюзу |
| `sse` | маршрут Server-Sent Events (Д5.3) | ваш `openapi.yaml` |
| `simulator_down` | маршрут, що тимчасово вимикає симулятор (О4.3) | [README симулятора](../tools/external-sim/README.md) |

Якщо шлях головної операції містить параметр, у `roles.main.path` задайте конкретний шлях до
підготовленого тестового ресурсу, наприклад `/v1/items/test-item`.

Для О6.2 засіб також надсилає збережені запити старого клієнта. Їхній формат описано в
[таблиці сумісності](compat-table.md).
