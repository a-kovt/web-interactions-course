# Сумісність версій (О6.2)

Під час поступового оновлення (О6.4) попередня версія N і нова N+1 працюють одночасно:
`app-a` уже новий, `app-b` ще старий, у браузерах відкрито сторінку старого клієнта, а в Kafka
лежать події старої схеми. Таблиця сумісності показує, які поєднання версій трапляються і чи
працюють вони. З неї випливають порядок оновлення й межа повернення попередньої версії.

Таблицю наводять у README проєкту. Рядок – хто надсилає (клієнт або видавець події), стовпець –
хто приймає (сервер або обробник). У клітинці – «так» або «ні», причина й тест, яким це
перевірено. «–» означає, що поєднання не виникає за вибраного порядку оновлення.

## Приклад: «Міська бібліотека»

Запланована зміна: замість лічильника вільних примірників `copies_available` книга має конкретні
примірники, а утримання – поле `copy_id`. Подія `hold.created` версії v2 додає `copy_id`.

| Клієнт \ сервер | N | N+1 |
|---|---|---|
| N | так | так: сервер і далі повертає `copies_available`, нове поле `copy_id` старий клієнт пропускає. Тест – повтор збережених запитів клієнта N |
| N+1 | ні: клієнт показує примірник з `copy_id`, якого сервер N не повертає | так |

| Подія \ обробник | N | N+1 |
|---|---|---|
| `hold.created` v1 | так | так: без `copy_id` сповіщення надсилається без номера примірника. Тест – подія v1 з фікстури |
| `hold.created` v2 | ні: обробник N не знає схеми v2 й переносить подію в карантин | так |

Висновки для цього прикладу:

- спочатку оновити всі екземпляри сервера, потім клієнт – клієнт N+1 із сервером N не працює;
- видавець починає надсилати v2 лише тоді, коли всі обробники вже N+1;
- розбір v1 в обробнику N+1 не видаляти, доки в брокері й карантині лишаються події v1.

## Збережені запити клієнта попередньої версії

Для тесту сумісності збережіть запити клієнта N у файлі проєкту, наприклад `docs/client-v1.json`.
На захисті викладач надсилає їх до нової версії сервера засобом перевірки (`check --replay`)
від імені звичайного користувача (не персоналу), тому файл має бути саме в цьому форматі.

Кожен крок містить `name`, `method`, `path`, за потреби `body` та очікуваний `status`.
Додаткові поля кроку:

- `idempotent` – надіслати новий `Idempotency-Key`
- `same_key_as` – надіслати ключ іншого кроку
- `save` – запам'ятати `id` відповіді під цим ім'ям, `{hold}` у шляху підставляє його
- `same_id_as` – відповідь має містити той самий `id`, що й збережений
- `if_match_from` – надіслати `ETag` відповіді іншого кроку як `If-Match`
- `fields` – поля, які читає старий клієнт, через крапку (`items.0.id`). Нові поля відповіді не заважають

Приклад для бібліотеки: список, створення утримання, повтор із тим самим ключем, читання.

```json
{
  "client_version": "1.0",
  "steps": [
    {
      "name": "list",
      "method": "GET",
      "path": "/v1/holds?limit=5",
      "status": 200,
      "fields": ["items", "next_cursor"]
    },
    {
      "name": "create",
      "method": "POST",
      "path": "/v1/holds",
      "body": { "book_id": "b01", "branch_id": "central" },
      "idempotent": true,
      "status": 201,
      "save": "hold",
      "fields": ["id", "status"]
    },
    {
      "name": "repeat",
      "method": "POST",
      "path": "/v1/holds",
      "body": { "book_id": "b01", "branch_id": "central" },
      "same_key_as": "create",
      "status": 201,
      "same_id_as": "hold"
    },
    {
      "name": "read",
      "method": "GET",
      "path": "/v1/holds/{hold}",
      "status": 200,
      "fields": ["id", "status"]
    }
  ]
}
```
